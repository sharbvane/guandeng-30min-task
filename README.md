# 渲染任务中断失败分析

## 我的判断

我拿到的是 2026-09-01 至 2026-09-07 的 1,127 行调度记录。去掉 54 行所有字段完全相同的重复记录后，得到 1,073 个唯一任务：895 个成功、133 个渲染中断失败、45 个超时未回传。

**最主要的可干预信号是：任务派发时，调度器持有的 Worker 最后一次心跳已经过期。**

把心跳年龄定义为 `dispatched_at - worker_heartbeat_at`，并把失败限定为 `status=0`（空值按题目定义算超时，不混入失败）：

| 心跳年龄 | 任务数 | 失败数 | 失败率 |
|---|---:|---:|---:|
| 小于 20 分钟 | 799 | 33 | **4.1%** |
| 大于等于 20 分钟 | 274 | 100 | **36.5%** |

两组的失败率相差约 **8.8 倍**；心跳年龄跨过 20 分钟后，失败率不是缓慢上升，而是出现台阶：

| 心跳年龄 | 任务数 | 失败率 |
|---|---:|---:|
| 0–10 分钟 | 414 | 4.1% |
| 10–20 分钟 | 385 | 4.2% |
| 20–30 分钟 | 46 | **41.3%** |
| 30–40 分钟 | 61 | 29.5% |
| 40–50 分钟 | 48 | 29.2% |
| 50–60 分钟 | 54 | 40.7% |
| 60 分钟以上 | 65 | 41.5% |

这不是“队列太长所以渲染慢”的直接证据。队列深度确实和失败相关，但按心跳年龄分层后，队列的增量信息很弱：心跳新鲜时，`queue_depth >= 50` 的失败率是 4.4%，`queue_depth < 50` 是 3.9%。更像是失败任务占住队列，导致队列堆积，而不是队列本身造成了中断。

低显存是次要放大器：心跳陈旧且 `memory_free_gb < 5` 的任务失败率为 43.1%（25/58），心跳陈旧且显存至少 5GB 为 34.7%（75/216）。但在心跳新鲜的条件下，低显存组只有 11.6% 失败（16/138），低于拦截重排的盈亏平衡线，单独按显存拦截不划算。

## 根问题

调度器的 Worker 健康判断使用了 `worker_heartbeat_at`，但从数据看，派发路径没有有效拦住过旧的心跳。只要最后一条心跳还在，节点就可能继续被当成“可用”，即使它已经失联、卡死，或心跳采集链路已经断了。于是任务被派到一个调度器“以为活着”的节点，渲染没有回传，最终成为 `status=0` 的中断失败；失败任务又继续占用队列，形成堆积和重试等待。

因此根问题不是某个模板或某个集群“渲染能力差”，而是**派发前的 Worker 健康准入没有把心跳新鲜度作为硬条件（或 TTL 设置失效）**。集群差异也支持这个解释：`cluster_sh_02` 的陈旧心跳组失败率为 47.4%，`cluster_bj_01` 为 43.4%，`cluster_gz_03` 为 36.9%；`cluster_hz_01` 是例外（12.3%），说明上线前还应单独检查该集群的心跳采集口径，但不能推翻全局信号。

## 做了什么

我实现了一个不依赖第三方包的可复现分析脚本 `analyze.py`，并把建议落成一条可执行的准入规则：

> **派发前检查：`dispatched_at - worker_heartbeat_at >= 20 分钟` 时，标记 Worker 为不健康，先刷新心跳或将任务重排到健康节点；不要直接派发。**

选择 20 分钟不是拍脑袋：题目给出失败损失 120 分钟、一次拦截重排 20 分钟，盈亏平衡失败率为 `20 / 120 = 16.7%`。20 分钟阈值下的实际失败率为 36.5%，明显高于盈亏平衡线；阈值从 15 分钟放宽到 20 分钟，净节省从 4,480 分钟提高到 6,520 分钟；继续放宽到 30 分钟，覆盖率下降，净节省降到 5,160 分钟。

按去重后的数据计算：

| 规则 | 拦截任务 | 捕获失败 | 失败召回率 | 净节省（分钟） |
|---|---:|---:|---:|---:|
| `lag >= 15` | 448 | 112 | 84.2% | 4,480 |
| **`lag >= 20`（主规则）** | **274** | **100** | **75.2%** | **6,520** |
| `lag >= 30` | 228 | 81 | 60.9% | 5,160 |
| `lag >= 20` 或 `memory < 5GB` | 412 | 116 | 87.2% | 5,680 |
| `lag >= 20` 或 `queue >= 50` | 685 | 118 | 88.7% | 460 |
| 仅 `queue >= 50` | 617 | 93 | 69.9% | **-1,180** |

主规则的 6,520 分钟是“拦截掉的失败 × 120 分钟 - 拦截次数 × 20 分钟”，相当于 7 天数据上约 **108.7 小时**的净算力/等待时间节省。这个数字假设被拦截的失败任务能够成功重排；如果重排只有 80% 能救回，净节省仍有 4,120 分钟（约 68.7 小时）。原始 1,127 行不删重复时，20 分钟规则拦截 291 个、捕获 105 个失败，净节省 6,780 分钟，结论方向不变。

这条规则不是“所有失败都能解释”：它覆盖 100/133 = 75.2% 的失败，剩下 24.8% 仍需要失败原因码或 Worker 日志。拦截的 274 个任务中有 161 个本来会成功、13 个是超时，它们会多等 20 分钟；这部分成本已经计入上面的 5,480 分钟拦截成本。

如果团队更看重“尽量少漏掉失败”，可以叠加 `memory < 5GB` 作为第二道预检；它把召回率从 75.2% 提到 87.2%，但会多拦 138 个任务，净节省反而降到 5,680 分钟。我的取舍是：**主规则只按心跳年龄拦截，显存作为告警/次级预检，不把队列深度作为主拦截条件**。

### 上线方式

1. 调度器在派发前读取 `now - worker_heartbeat_at`；超过 20 分钟直接进入“刷新心跳/重排”分支。
2. 把 Worker 健康状态从“有历史心跳”改成“心跳在 TTL 内”，同时记录心跳年龄、集群、节点和重排结果。
3. 先影子运行 1–2 天：只记录“本应拦截”的任务，不改变真实派发；确认拦截量、重排成功率和队列延迟没有恶化后再强制。
4. 对 `cluster_hz_01` 单独核查心跳 agent/时钟；对超时（空 `status`）单独建监控，本次数据只能确认超时占 4.2%，不足以把超时归因于心跳。

## 怎么证明有用

`analyze.py` 从发放的 CSV 重新计算所有数字，并输出：

- `outputs/summary.json`：数据质量、状态分布、主规则和成本口径；
- `outputs/lag_bins.csv`：心跳年龄分箱的失败率；
- `outputs/rules.csv`：不同拦截规则的覆盖率、召回率和净节省；
- `outputs/segments.csv`：集群/模板的失败率；
- `outputs/lag_by_cluster.csv`：集群内“新鲜/陈旧心跳”的对照；
- `outputs/task_level.csv`：去重后的逐任务审计表。

复现命令（Python 3.11，标准库即可，无需安装依赖）：

```bash
python analyze.py --input data/render_tasks.csv --out outputs
python -m unittest discover -s tests -v
```

测试覆盖了时区归一化、状态语义和主规则的关键数字；如果脚本或数据变化导致 1,073 / 133 / 274 / 100 / 6,520 这组结果不一致，测试会失败。

## 数据质量与口径

- 原始文件：1,127 行，UTF-8 CSV，SHA-256 `73E63B8B449FC795DD0FB2BD9A93E6D79AB17C53703F0B6F9925AD12FF28FF51`。
- 54 行是**所有字段完全相同**的重复记录，不是带不同派发时间或结果的重试记录；主分析去重，原始行结果作为敏感性分析保留。
- `status=1` 为成功，`status=0` 为失败，空值为超时；空值没有被算进失败率。
- `dispatched_at` 带 `+08:00`，`worker_heartbeat_at` 是 UTC `Z`；脚本统一转 UTC 后计算，避免把 8 小时时区差误当成心跳年龄。
- 只使用发放的数据，没有补造数据，也没有用外部数据支撑结论。

## 局限

- 这是观察性数据，不是随机对照实验；“心跳陈旧 → 失败”是当前数据支持最强、最可执行的解释，不是已证实的唯一因果链。
- 数据没有 Worker ID、失败原因码和重试历史，无法区分节点宕机、网络分区、心跳 agent 故障或调度器时钟问题；20 分钟规则解决的是“不要把任务派给状态不可信的节点”，不是修复心跳链路本身。
- 6,520 分钟是按题目给定的 120/20 分钟做的成本估算，不是实际账单；重排成功率未知，已额外给出 80% 救回率的敏感性结果。
- 超时（45 个，4.2%）与心跳年龄没有明显单调关系，需要单独的队列/回传链路排查。
